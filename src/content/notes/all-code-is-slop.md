## 产量增加之后，工程师要解决什么问题

### 演讲的出发点：让质量跟上吞吐量

原视频题为 All Code Is Slop (Except Mine)，以“别人的代码都是垃圾，只有自己的例外”自嘲式开场。这里的 slop 指缺乏可靠设计、靠补丁堆积起来的低质量代码。Lauren Tan 自述，上月个人向生产交付了约3000个 PR；她关心的核心问题是，当智能体让每个人都能大量生成代码时，怎样维持甚至改善质量。

这改变了工程师的工作重心。以前逐个检查同事的少量修改还可能跟得上；当输入接近连续的代码流，人工注意力会成为瓶颈。讲者因此把“软件工厂”的前提压缩为一个词：信任。她描述自己花约六个月投资环境，才逐渐达到能够放心交付大量 PR 的状态。

> <strong>本讲的核心命题</strong>
>
> 可靠的高产量依赖一个能持续约束、运行和验证代码的环境。工程师要把判断沉淀到接口、架构和工具反馈中，让后续修改更容易沿着正确路径完成。

### 信任倒金字塔：先把投入放在哪里

讲者的倒金字塔从上至下依次为代码库、静态分析、验证、文字规则、人工审查。上层覆盖更广的基础，下层保留更依赖具体判断的工作；左侧还标注了向下的成本箭头。这是一张投入优先级的概念图，没有给出定量成本模型。

代码库这一层包含好的 API、架构和重构。第二层在幻灯片上称为 static analysis，并列出 lint、类型、编译器、测试与 CI；这里按讲者的宽泛分类理解，不把测试严格归为静态分析。接着是运行验证与形式验证。规则、skill、AGENTS.md 等文字材料用于补足需要判断的内容，最后仍有人工审查。

> <strong>为什么“确定性”值得优先投资</strong>
>
> 文字要求需要智能体理解并持续记住；编译器、导入检查或 lint 可以对实际变更反复执行。某次错误被编码为明确检查后，下一位智能体也能收到同样的反馈，团队不必依靠同一个人再次提醒。

### 本章小结

产量提升使质量控制更依赖环境。先改善代码和可执行约束，再逐步叠加验证、文字指导与人的判断，是整场演讲的组织主线。

## 代码库会教智能体：从修补走向架构约束

### 为何旧技术债会影响新产出

智能体的输出取决于输入，而代码库是最大的一类输入。一个 workaround、弃用接口或反模式，只要在仓库里反复出现，就可能被当作既定惯例继续复制。讲者用“园艺”说明这个反馈过程：架构和约束是新代码生长的地基，坏模式则像会蔓延的杂草。

这意味着清理历史代码的收益会延伸到未来产出。纠正单个 PR 只改变一个实例；修正大家模仿的示例、收紧接口并阻止反模式新增，会改变后续许多修改的方向。

> <strong>把一次纠错转化为一种能力</strong>
>
> 遇到重复问题时，依次检查：能否通过更好的 API 消除误用空间？能否通过架构隔离危险路径？若仍需约束，能否写成 lint、类型或依赖规则？能够执行的部分应成为下一次修改的即时反馈。

### Dune：集中承接难以正确使用的机制

Dune 是讲者团队为 Grok Bot 构建的客户端框架，她把它类比为面向 Electron 应用的 Next.js。框架本身的技术新颖性并非重点，重点是把桌面开发经验编码为结构和规则。

React 的 useEffect 是具体例子：它有合理用途，但在生命周期、依赖与副作用处理上需要细致判断。团队选择禁止产品代码直接使用，仅在 Dune 内部的有限位置允许使用。这样把复杂性集中到框架维护者能够控制的地方，产品开发沿着更受约束的 API 进行。

> <strong>框架经验的适用范围</strong>
>
> “禁止 useEffect”是讲者团队的产品代码规则，不能据此推导所有 React 项目都应禁用它。可迁移的原则是：为高频误用机制提供更清晰的接口，并将必要的复杂处理集中封装。

### 目录结构也是上下文

Electron 的 main 与 renderer 有不同职责。讲者回忆，智能体曾把主进程代码引入渲染进程，造成长任务与界面卡顿。Dune 将边界直接命名为 electron-main 与 electron-renderer，并由依赖图分析与 lint 阻止跨边界导入。

### 本章小结

代码库既是实现，也是后续智能体的示范。清理旧模式、封装复杂机制、把目录边界变成依赖规则，可以减少整类错误进入人工审查的机会。

## 为什么快速补丁和解释性注释会扩散

### 183个计时器的故事

讲者在 Cursor 的经历揭示了一个扩散链条：VS Code 的命令式机制与 React 的声明式风格之间出现架构冲突，智能体用 setTimeout、requestAnimationFrame、requestIdleCallback 等方式延后操作，暂时绕过问题。

幻灯片中的最初修改用零延迟 setTimeout 延后 release，以修复闪烁，并留下“以防它回来，稍后释放”之类的注释。随后模式被复制进公共模块，最终出现183个计时器。讲者把大量计时器的创建与销毁，同垃圾回收压力和界面卡顿联系起来。

问题不在于所有计时器都不合理，而在于局部修复被当作架构问题的长期答案。注释写出了看似充分的理由，后续智能体又把这些理由和代码一同复制，补丁遂成为惯例。

### 注释能解释，检查才能约束

讲者称团队在 Grok Bot 中禁止了约99%的代码注释。她的理由是：注释会过期，读者不一定阅读，它还能成为智能体解释自己为何不修根因的出口。另一方面，智能体也可能把一次小纠正过度泛化成永远不能破例的文字规则。

> <strong>理解这项激进选择的真正用途</strong>
>
> 演讲中的禁注释政策属于具体团队实践。不能把它扩展为删除所有背景、设计原因或接口文档的普遍建议。这里要保留的工程信号是：一条能被机器判定的要求，若只写在注释中，就没有获得实际执行能力。

团队转而提供能指导修复的 lint 错误消息，让智能体处理根因。一个好的报错需要说明违反了哪条结构约束，并指向正确接口或修改方向。它同时承担拒绝错误与引导下一步行动两种责任。

### 把评审负担逐渐变小

讲者提出，每次纠正智能体，都应考虑转为确定性检查，或通过 API、架构从类别上消除问题。这样未来审查需要反复关注的事项会越来越少。在她描述的成熟环境中，大多数 PR 因而能够由智能体自行合并。

> <strong>纠错的累计收益</strong>
>
> 重复人工指出同一问题，成本会随修改数量持续增加。将问题固化为可执行约束，可以让同一判断被大量修改复用；真正需要人工判断的部分因此更集中。

### 本章小结

快速补丁会通过代码库的示范效应扩散。应把修复指向根因，并把能够执行的规则落在 API 和检查工具上；注释承担解释责任时，也应保持与实现一致。

## 让智能体运行真实应用，并提交验证证据

### 运行验证从可操作的环境开始

讲者说，他们的代码审查逐渐转为检查视频、截图、图解和形式验证产物。最基本的运行验证，就是让智能体能启动真实应用，并使用人类开发者也使用的调试工具，例如 Chrome DevTools Protocol。

若智能体只能读写源码，就难以发现“代码看起来正确，但真实操作不工作”的问题。运行能力让修改、观察、定位、再修改组成闭环。人类可以据此查看最终行为及关键状态，而不完全依赖实现者对正确性的口头描述。

### Feature map：功能、入口、验收证据

Feature map 从用户视角描述应用。幻灯片用三个问题概括它：有哪些功能？用户怎样到达？什么证据能说明它工作？这比只罗列组件名称更接近验收需求，也为“左侧栏那个东西”提供共享词汇。

CLI 负责把功能入口变成稳定操作。画面展示的例子依次点击名为 Settings 的可访问元素、取得应用快照、保存截图。以下命令来自幻灯片，是讲者的自定义应用驱动示意，不能当作本机已经安装的通用命令。

``` bash
app aria-click --accessible-name "Settings"
app snapshot
app screenshot proof.png
```

可复用 CLI 让智能体无需每次重写驱动脚本，从而减少 token 消耗；驱动自身也能够测试。Feature map 说明去哪里、看什么，CLI 提供怎样操作的稳定接口。

> <strong>整理者补充：如何把模糊需求转成验收任务</strong>
>
> 以“设置页打不开”为例，可以记录功能入口、点击动作、预期设置面板、失败时的界面状态和截图。这样用户说的功能名称、智能体执行的操作和评审者看到的证据指向同一件事。这是对 feature map 思路的教学示例，并非视频中的具体故障。

### 本章小结

运行验证需要实际可操作的应用、从用户视角整理的功能地图，以及稳定可复用的驱动。证据的价值来自它对应了具体行为和预期结果。

## 形式方法、性质测试与状态图各解决什么

### TLA+与Lean：把不同问题交给不同工具

讲者正在试验形式验证。TLA+ 用于对重大用户流程进行模型检查，例如跨设备、跨平台通知；Lean 用于特定算法的证明，例如自研虚拟化库中与闪烁、抖动相关的算法性质。

<figcaption>讲者对两类形式工具的定位：状态模型检查与针对算法的证明。</figcaption>
</figure>

<p class="source-note">视频画面时间区间：00:10:50–00:11:33。图为原始幻灯片区域裁剪。</p>

TLA+ 的关注点是状态、转换和希望始终成立的规则；Lean 的关注点是把需要证明的逻辑步骤形式化。两者都要求人和智能体说清“正确”究竟指什么。它们已经帮助团队发现一些 bug，但讲者明确说仍在实验，并将其作为环境中的另一层工具。

> <strong>形式验证的结论范围</strong>
>
> 整理者补充：模型或定理的结论依赖所写下的假设与性质。模型检查通过不自动意味着整个产品没有 bug，算法证明也不自动覆盖 UI、运行环境或所有实现细节。选择工具时应先说明要验证的具体性质。

### UI性质测试：探索操作组合

讲者还展示了 UI property-based testing，称它已经发现若干界面 bug。这类方法围绕应保持的性质探索多种输入或操作组合。相比只测试一条固定脚本，它能帮助发现不常见的状态路径。演讲没有展开该演示的完整测试规范，因此本讲义不把它补写成一套未经展示的测试结果。

### 状态图帮助评审需求理解

讲者展示 pstack 插件中的 /statechart，将状态机从用户视角画出来，再与视频、截图一起审查。图能让人更容易提出具体问题：某状态能否到达？动作后会进入哪个状态？是否漏掉了取消或失败路径？

状态图因此兼顾需求澄清与实现验证。讲者强调，形式方法也帮助判断智能体是否理解人的目标；如果模型表达的流程就与预期不一致，继续打磨实现仍可能做错产品。

### 为什么验证值得消耗更多token

演讲引用 Cindy 的经历：六个月前因细微 bug 难以信任智能体，后来每日约70%的 token 用在验证上。讲者说自己的大部分 token 同样用于验证。这个百分比来自引用个案，不是建议所有项目照搬的预算。

> <strong>智能体改变了验证的成本结构</strong>
>
> 测试、模型检查和算法证明大多已有历史。智能体降低了理解、编写与使用这些工具的成本，使过去难以投入的验证更容易开展。生成代码省下的成本可以转投到检查结果是否符合目标。

### 拓展阅读

- [Cursor plugins：pstack](https://github.com/cursor/plugins/tree/main/pstack)，视频幻灯片给出的验证与状态图工具入口。

### 本章小结

运行证据说明真实应用发生了什么；性质测试探索输入与操作组合；状态模型和证明帮助精确表达正确性。它们可以互相补足，选择依据是当前要回答的问题。

## 总结与延伸

### 讲者的结尾：先修内循环，再扩展外循环

在搭建软件工厂、自动编排大量任务之前，讲者建议先改善代码库：每次纠正智能体时，先用 lint 防止反模式新增，再清理旧实例，并建立扎实的验证流程。如果内部编码循环持续产出低质代码，自动化只会放大问题，并消耗更多 token。

讲者随后给出外循环实例：每次发版后，通过 Grok Bot 的例程启动 Cursor 任务，对整个应用进行 fuzz，像真实用户一样运行并操作；发现 bug 后分别打开修复 PR，并在其环境下自动合并。她将这种自主性归因于代码库及验证基础已经成熟，而非简单地增加任务并行数。

> <strong>整理者的概念压缩</strong>
>
> 自动化的可靠性取决于被自动化循环的质量。代码库提供示范与结构，静态检查限制错误路径，运行和形式验证提供证据，人的判断负责目标与剩余不确定性。

### 把各章连成一个改进闭环

一次错误可以成为下一轮环境改进的输入：先识别它属于接口误用、架构冲突、状态遗漏还是实际运行故障；在对应层修复根因；把可重复的判断交给工具；再用真实行为和必要的模型证明验证修改。下次智能体进入相同场景时，就能从代码示范和即时反馈中获得更好的起点。

这也解释了代码清理与验证投资为何互相促进。干净的示例降低错误被复制的概率，可执行约束减少常见失误，稳定驱动降低取证成本，状态模型又暴露实现前的理解偏差。每层都减少下一层需要承担的判断压力。

### 可执行的起步顺序与开放问题

1.  从最近重复出现的一类错误入手，确定根因和受影响路径。

2.  改善 API 或目录边界，加入能够直接判定该错误的检查，并清理历史示例。

3.  为关键用户流程写出 feature map，明确入口、动作、预期状态和证据。

4.  复用应用驱动，使智能体能运行、观察、修复并再次验证。

5.  对复杂状态或关键算法选择适合的模型检查、性质测试或证明，再逐步扩展自动编排。

以上顺序是基于视频观点整理的实践建议。仍需结合项目回答：哪些性质值得形式化？哪些修改需要人的判断？运行证据是否覆盖了用户目标？如何同时衡量交付价值、故障和资源代价？演讲没有给出统一阈值，答案取决于具体产品与风险。

### 本章小结

本讲最有价值的迁移点，是把纠错沉淀为环境能力，并用可复核证据支持自主性增长。当内循环稳定后，外层软件工厂才有可靠基础；速度和质量可以共同改善，但仍需持续观察实际代价。
