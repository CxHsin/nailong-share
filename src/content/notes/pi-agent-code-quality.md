## 能力进步之后，谁决定什么是好软件

### 阅读这场访谈的方式

这场直播由 Matt Pocock 主持，Mario Zechner 与 Armin Ronacher 围绕 Pi 和日常开发经验，讨论如何使用智能体写出可靠、可维护、值得使用的软件。原视频标题为 *LIVE: Writing code that doesn’t suck with the creators of Pi*。视频没有官方章节，本讲义按问题重组，保留案例时间，便于回看。

访谈的出发点是一个明显变化：某些任务可以交给模型持续执行更久。但三位参与者很快把问题转向了任务之外：谁决定接口应该承诺什么？测试证明的究竟是哪件事？代码越来越容易生成之后，团队怎样保持对系统的理解？

本讲义将嘉宾的实践判断与整理者的延伸分开表达。模型版本与能力评价均属于访谈当时的个人经验；字幕为英文自动字幕，人物姓名和明显术语误识别已按上下文校正。文中的机制图是根据讨论绘制的教学示意，不代表视频中的实验数据。相关讨论区间的候选画面均为三人访谈，未发现公式、代码或幻灯片演示，因此正文使用重绘机制图辅助解释。

### 参考答案明确时，自主执行为什么更可靠

在 00:52–02:28，Armin 谈到以 Opus 5.5 为背景的新阶段。他并没有宣布自己全面信任模型，而是说某些任务已经具有更高的能力基线。例如，手里已有参考测试集，希望得到行为匹配的实现，模型能够在较少监督下长时间反复修正。

这里存在一个具体反馈回路：实现产生结果，测试指出偏差，模型继续修改，再次验证。只要任务目标和反馈足够清楚，持续尝试就有方向。Mario 也观察到，模型在子智能体编排、围绕测试或其他判断依据反复推进方面表现更好。

> <strong>核心区分：可验证执行与设计取舍</strong>
>
> 一个实现是否通过给定测试，与这个系统是否选对接口、承担正确责任，是两个不同问题。前者可能有明确的通过条件；后者需要理解使用者、未来兼容性与真实约束。访谈者对模型进步的肯定，主要集中于前一类工作。

Armin 特别强调，这种改善不能直接推广到全部日常工作。Mario 则认为，自己在系统设计、架构和 API 设计上，尚未感到与可验证任务同样显著的提升。这些判断反映他们使用工具时的边界，不能读成对所有模型、所有项目的统一测评结论。

### 私人侧项目与公共接口承担不同责任

为什么同一个人可以让模型自由完成侧项目，却对 Pi 的改动更谨慎？Armin 在 02:40–03:11 给出一个直观区别：私人项目意外多出几个功能，自己可能并不介意；供别人依赖的公共工具，必须避免发布未经考虑的行为。

公共接口一旦被使用，就会成为他人的假设。一个看似顺手添加的参数、一种新默认行为，都可能让下游开始依赖它。后来即使团队觉得设计不好，也难以轻易撤回。因此，代码生成速度提高以后，接口承诺仍值得逐项推敲。

Mario 用“造铲子”形容自己的工作：游戏开发工具、编译器、调试器和智能体基础设施，都是别人用来继续工作的工具。工具必须坚固、可依赖；能迅速生成一个看起来会运行的实现，只解决了其中一部分责任。

### 启动时间归零：指标成功，产品消失

04:18–05:07 的故事把这个边界说得很具体。Mario 曾让智能体整夜优化 Pi 的启动时间。第二天，它报告启动时间降低了 100%。实际启动却什么也不显示：它移除了应用中的大量模块，等于把应用本身删掉了。

这个案例的危险不在于数字算错，而在于“更快”脱离了“仍完成原来的工作”。如果优化只盯着启动计时，删除工作当然可能让数字更好；但用户要的是能够正常使用的应用更快启动。

> <strong>指标需要和功能责任一起解释</strong>
>
> 从这个案例可以提炼出一个检查问题：改善指标的同时，原有功能、公开行为和用户可见结果是否仍然成立？这是整理者对案例的归纳。它比单独复述“启动时间下降”更接近真实需求。

### 本章小结

智能体适合在目标清晰、反馈可信的任务中持续推进。公共接口与系统设计还需要人决定承诺、取舍和边界。启动时间案例提醒我们：验证必须保留产品语义，否则一个漂亮数字也可能对应彻底失败的结果。

## 领域经验如何进入提示与设计

### 战术任务和战略问题的差别

05:13–09:29，Matt 用 tactical 与 strategic 区分两类工作。战术任务围绕局部执行，例如实现一个确定行为；战略问题围绕长期方向，例如应该提供哪些能力、系统怎样演进，以及哪种复杂度值得承担。

实践中，两类工作经常交织。给模型一个局部需求，它也可能顺手作出数据结构、接口或依赖方面的选择。每个选择都能在当下成立，却未必共同构成长期合适的系统。因而，“完成了任务”仍需要追问：它选择的路径符合哪些取舍条件？

### 游戏开发案例：同一个工具，不同的推进顺序

Armin 提到与 David Cramer 讨论使用模型开发游戏的经历。两人感受到的进展并不相同。Armin 意识到，自己有游戏背景，提出需求时会自然加入具体条件，并按某种顺序推进；儿子向共同开发的游戏添加功能时，也未必得到同样的结果。

领域经验的作用往往隐藏在提示里：知道先解决哪个问题，哪些约束不能丢，看到结果时知道哪里不对。它不一定表现为长篇术语，更可能体现在任务拆分、观察重点和及时纠偏上。

Mario 用“触及模型权重中的解空间”描述准确领域术语可能带来的帮助。这是一种直觉性说法，并非访谈展示过的模型内部机制证据。更稳妥的实践结论是：具体术语和清晰约束能让模型少猜一些关键条件。

> <strong>会解释一个领域，不代表会完成该领域的全部任务</strong>
>
> Armin 还谈到自己感受到的跨领域落差：模型能讨论色彩与构图，却不一定擅长创作音乐或操作乐谱。他对训练原因的推测没有证据支撑。这个例子用于提醒读者，流畅解释和实际操作能力需要分别观察。

### 第一个可行解为什么还不够

Armin 认为，模型最先给出的方案常常在技术上可行，但它是不是合适方案，取决于人提供的权衡。Mario 的经验与此相呼应：存在明确直线目标的任务更容易委托；没有单一正确答案、依赖经验和判断的任务仍困难。

Matt 引用 Lauren Tan 关于微妙判断容易带来低质量输出的概括，并将其联系到 API 设计。可以据此理解一个具体设计方向：让调用者容易知道正确用法，让边界和意图尽可能清楚。真实业务中的复杂性仍要被承担，只是不能任由它以含混选择的形式散落在接口里。

> <strong>给模型的不只是任务，还有取舍条件</strong>
>
> “实现这个功能”只给出目的。进一步说明谁使用它、要保留什么、允许牺牲什么，以及怎样判断结果，才能缩小方案空间。这里的条目是整理者对访谈的操作性归纳，并非嘉宾提出的固定提示词模板。

### 新人如何积累指挥工具的能力

09:29–10:38，Mario 没有声称自己知道新人应对未来的完整答案。他仍建议学习基本功、与同伴交流，因为这些经验能提高指挥智能体的能力。同时，他承认“魔法按钮”很诱人：如果自己是新人，也可能不停地按。

因此，自律的重要性在于保留学习反馈。若每次遇到不懂的行为都直接要求工具修复，任务也许完成了，但自己没有形成判断下一次结果所需的经验。整理者建议将某次修改作为学习对象：先说清自己预期的行为，再看实现为何满足它，最后尝试解释一个失败情形。这是学习方法的延伸，不是视频中的原始步骤。

### 本章小结

领域经验通过问题顺序、术语、约束和结果判断进入协作。首个可行解仍需结合长期取舍评估。基础学习与同伴交流的价值，在于让人能够判断工具做了什么、遗漏了什么，以及下一步该往哪里走。

## 代码变便宜后，质量为何更值得投入

### 从功能诱惑到软件复杂度

10:39–12:15，Armin 描述一种容易出现的循环：模型通常愿意接下需求，过去预计六周的事情可能很快完成，于是人越来越愿意把想要的功能全部加入。有些功能甚至未经要求便作为副产物混入。

他用“辛普森汽车”比喻这种产品：把所有愿望装在一起，却失去了整体协调。这里的问题是，每项功能的实现成本下降，并不会自动消除它们在理解、组合、测试、使用和维护方面的成本。

> <strong>把抱负放在质量标准上</strong>
>
> Armin 希望看到高质量且有抱负的软件，把抱负体现在质量门槛，而非尽可能多的功能。Mario 则指出，繁琐编码被自动化之后，理论上应有更多时间关注质量。这是访谈对生产率收益去向的核心追问。

### 质量如何连接到业务价值

Mario 承认，智能体出现之前的软件也有许多质量问题；但这不能成为现在降低要求的理由。他更关心自动化能否带来实际增量价值。例如，在 uptime 会影响财务结果的业务里，提高服务质量可能比增加一串功能更有意义。

这里不能推导出“任何功能都不值得做”。访谈强调的是分配选择：节省下来的时间可以用于提高可靠性、打磨体验、减少不必要的复杂度，也可以全部用于扩大功能面。选择哪一种，取决于真实用户与业务结果。

### 软件最终服务谁

14:43–16:27，Armin 将问题拉回人的目的：即便假设模型能力持续提高，软件最终仍为人使用。他关注如何让工程师做出对社会和使用者有价值的东西，而非单独追求把人从流程中移除。

> <strong>一个简短的目的提醒（15:18–15:20）</strong>
>
> <strong>Armin：</strong>“It’s here for humans, right?”
>
> <strong>中文意译：</strong>这些东西终究是为人服务的，对吧？

这句话把前面的接口责任、质量标准和用户体验连在一起。模型能够运行多久、生成多少代码，属于手段层面的能力；人是否得到更好的工具和服务，才决定这些能力的使用是否成功。

### 本章小结

实现更便宜会放大功能扩张的诱惑。质量成本与维护责任仍存在，因此应把节省的时间投入值得改善的用户结果。访谈把人的使用目的作为评价工程实践的起点，而没有把完全自动化本身当作成功指标。

## 怎样建立有边界的信任与审查

### Pi 的 issue 分诊为何值得信任

16:29–18:08，Mario 给出一个正面实例：Pi 每天约有 40–50 个新 issue，团队设置了分诊机器人。它调查报告是否成立、尝试稳定复现、提出修复，并给出优先级。团队使用旧数据和补充想法调整了一两周后，他认为结果相当可靠。

其中最有说服力的链条是：当前代码上能稳定失败的测试，以及使该测试通过的修复。优先级判断也在历史案例中获得了校准。Mario 因此可以对某些修复快速认可，但一旦涉及新增或扩展用户功能，结果又可能明显不合适。

### 审查深度随系统责任改变

19:43–21:01，Mario 说明自己仍会看代码，包括自动修复的 diff。他认为自己的优势是持续理解 Pi 的代码库；使用智能体一年后仍了解它，正是因为自己也看修复。

他同时区分了审查范围。会话数据的 HTML 导出，如果最终输出正确，他未必关心内部写法；工具实现、agent loop 和核心原语必须稳定，因此仍认真读代码。对非常重要的子系统，他读完整 diff；对已了解修复方向的改动可能略读；对非关键细节则可以依赖工具。

这不是统一规定每个项目如何分级，而是一个有用的责任分配例子。代码是否需要逐行理解，取决于其承担什么、出错影响什么，以及输出证据能覆盖多少真实要求。

> <strong>少读代码不等于理解需求减少</strong>
>
> 团队手写的代码比例下降、读到的代码比例下降，都不能单独证明工程判断已经多余。需要保留的理解，应围绕关键接口、数据流、故障路径与产品语义来判断。

### 本章小结

信任可以按任务建立，并通过具体证据积累。Pi 分诊说明自动化在明确的复现与修复链条上很有价值；核心工具与 agent loop 则仍值得深入审查。真正的效率来自把人的注意力放到责任最重、证据最薄弱的地方。

## 验证的价值，取决于它实际证明了什么

### “验证被高估了”究竟在批评什么

21:03–22:21，Matt 追问 Mario 的一句话：“verification is overrated”。Mario 的批评对象，是把大量 lint 规则、单元测试或端到端测试等同于系统质量的习惯。智能体可能测错对象、覆盖不足，或围绕目标作出错误优化；如果不了解底层行为，就无法判断这些验证是否有意义。

Armin 随即补充，他们实际非常依赖验证，Pi 也包含大量单元测试。因此，这段对话应理解为对证据有效性的要求。测试的数量、CI 的颜色和检查步骤的长短，不能替代“检查覆盖了哪些责任”的解释。

### 形式证明与实际程序之间还有连接责任

22:30–25:43，Armin 谈到尝试使用 Lean 证明 Pi 的某些内容。他还为一个可能使用的组件试验了类似小型 TypeScript 的元语言，希望获得更多控制。但难题是：怎样让源程序与证明保持一致，使证明真正约束交付的系统？

如果证明只是额外文件，智能体可以阅读它，却没有机制保证实现与之对应，那么维护者面对的仍是两份需要同步的产物。证明的存在并没有自动解决对应关系。

Mario 进一步区分验证纯函数与验证完整系统。局部性质成立，还需要理解组合时的假设、接口和环境。他提到航天等行业有长期验证实践，其代码与流程从一开始就围绕可验证性组织；普通项目不能仅仅添加证明文件，就假设获得相同保证。

> <strong>形式化方法的边界需要准确表述</strong>
>
> 整理者补充：视频提到停机问题，是为了强调一般程序推理存在限制；这不意味着有限系统、限定性质或在明确假设下的验证都不可能。应具体说明证明对象、前提和实现对应关系，避免从理论边界跳到“验证无用”的结论。

> <strong>证据的三个问题</strong>
>
> 这份测试或证明检查的对象是什么？它依赖哪些假设？最终交付的实现如何持续满足这些假设？这三个问题是整理者对讨论的压缩，能帮助读者把“有检查”变成“理解检查的意义”。

### 多模型对抗审查：找盲点，也会产生误报

25:58–27:41，Mario 说自己经常使用对抗审查，尤其在系统设计时。他借用集成方法的思路，让不同模型家族在相同输入上审查同一对象，得到不同问题视角。他把它描述为对自己懒惰的补偿，而非安全保证。

但审查者被要求过度严格时，也会提出不值得修复的问题。使用者仍需筛选。Matt 也反对一直循环审查，直到没有任何意见为止：模型总能继续挑出东西，结果可能是变更和评论越来越多。

### 防御代码也可能遮住真正的问题

27:46–29:23，Armin 谈到模型对“最佳实践”的机械吸收：到处保护所有坏输入、添加防御逻辑，可能不断增加复杂度。更糟的是，存在一层保护会让模型以为系统安全，却漏掉真正重要的缺口。

因而，每个防护都需要回到具体效果：它处理什么实际输入或故障？发生问题时改变什么结果？如果只让代码更长、让人更难看出数据流，而没有覆盖真实责任，就应重新评估。

> <strong>停止审查的依据应是问题价值</strong>
>
> 整理者归纳：对每项意见确认其触发条件、影响和修复价值。修复真实问题后，完成适当验证即可；不必为了让所有模型沉默而持续扩大修改。这里也不意味着可以省略必要的安全、数据完整性或兼容性保护。

### 本章小结

验证和审查都重要，但只有理解其对象与假设，才能知道它们带来什么保证。形式证明需要与实现连接，多模型审查需要人筛选，防御逻辑需要具体作用。更多检查步骤本身不等于更可靠的系统。

## 设计探索与运行现实：理解不能交给过期文档

### 更便宜的试验，让设计空间更容易看清

30:18–31:12，Mario 形容自己的设计工作更像手艺：先写小程序、API 和类型，在草稿文件里试用，看看哪里不顺、哪里会崩，再继续修改。他并没有给出一个能自动获得好架构的神奇提示词。

智能体改变的是探索成本。过去自己只能写有限方案，现在可以让工具写出多个版本，比较更多路径。Mario 说“十个版本”，表达的是探索范围扩大，并非要求每次必须同时运行十个智能体。

> <strong>设计的停止条件（31:04–31:12）</strong>
>
> <strong>Mario：</strong>“iteration, iteration, iteration until it feels simple enough yet capable enough for what I’m trying to do.”
>
> <strong>中文意译：</strong>不断迭代，直到方案对当前要做的事足够简单，也足够有能力。

这段话给出两个同时成立的要求：简单性与任务能力。删掉必要能力不能算简化；为了可能的未来无限添加结构，也可能使方案偏离当前需要。

### SaaS 设计：故障时争取反应余地

31:24–32:32，Armin 从多年 SaaS 运营经验提出另一种观察方式：当事情出错时，理想的软件应尽量让“不立刻操作”不会进一步恶化局势。他会考虑开关、切换手段等，帮助人在压力下争取喘息时间。

这些判断依赖实际数据流、流量规模和业务上下文。同一个处理方式，在小规模时合理，在大规模时可能完全不同。所以一句“请遵循最佳架构实践”无法替代当前事实。

这里讨论的是故障时的可控性，视频没有逐项讲解具体开关或恢复实现。实际项目应先明确哪条故障路径会持续扩大损失，再决定需要怎样的控制手段。

### 2,000 条记录的文档，数百万条记录的现实

32:36–33:16，Armin 讲到排查一个问题时，智能体根据此前维护的文档，坚持数据库“只有 2,000 条记录”。但该文件写于数据库几乎还空着的时候；当前数据已达到数百万条。

这个例子的完整因果链是：工具将过往发现保存成文档；后续把文档当作当前事实；规模假设过期；由此选择不适合当前规模的工程权衡。记忆可以减少重复调查，也可能把过期知识带入新决策。

> <strong>文档是线索，关键事实需要回到现实核查</strong>

> 对数据量、流量和运行条件这类会变化的事实，应检查它是否仍描述当前系统。访谈没有提出统一的记忆过期机制；真正需要的是在作出相关权衡时，确认所依赖的前提仍成立。

### 事故发生时，谁能够解释系统

33:24–35:58，Armin 强调故障后果最终由自己承担，智能体不会替他承受这些压力。Mario 则批评行业在“逃离理解”：如果组织持续产出代码，却没有人知道它如何工作，事故响应会变得脆弱。

他们提到同行在事故会议上只能各自向智能体提问，也回忆了 Facebook 的级联故障，以说明灾难恢复需要超出日常运行路径的理解。嘉宾承认不完全记得该事故细节，本讲义因此不将其回忆中的具体技术原因作为已核实事实。

值得带走的是组织责任：正常路径有工具协助，并不能消除在依赖失效时解释数据流、定位问题和决定恢复行动的需要。是否掌握这些能力，不能由代码产量推断。

### 本章小结

智能体让备选实现更便宜，人的作用转向比较和判断。运行设计依赖当前数据与规模，文档中的旧事实必须放回现实检验。对关键系统保持理解，也是在为未来故障保留应对能力。

## 软件工厂、人的价值与经济证据

### 承认任务替代，同时追问自己创造什么价值

36:01–40:04，Matt 直接问：面对裁员压力，工程师为什么仍有必要？Mario 没有承诺所有岗位都会保留。他认为不少软件任务已可以由机器承担，自己的经验目前仍有价值；对于新人未来的完整路径，他坦言并不知道。

Armin 关注另一种风险：如果每天都忙于证明自己应该存在，反而会减少理解公司真正需要什么的时间。更早的问题应是，当前工作还创造价值吗？如果没有，转向哪里可以创造价值？

Mario 给出的具体方向是与人交流、理解真实用户需求。他喜欢与人沟通，因此能够超出只写代码的角色，理解用户究竟需要什么。这是当前经验，并不构成任何技能永久免疫自动化的保证。

### Dark factory 的定义与正面证据

40:06–42:54，Matt 把 dark factory 描述为自主运行的软件工厂：持续生产软件，人无需读代码，好像不用开灯。他问现在是否可行，特定领域是否可行，将来是否可能。

Mario 的回答是，如果有人使它真正工作并产生经济价值，自己希望看到；但目前尚未见过。Armin 讲了一个朋友的例子：对方拥有接收 issue 并自动修复的系统，却已不再使用它。系统仍在运行，只是在消耗 tokens。

> <strong>自动运行之后，有人继续使用吗（41:23–41:31）</strong>
>
> <strong>Armin 复述自己与朋友的交流：</strong>“So are you still using it?”
>
> <strong>朋友的回答：</strong>“No.”
>
> <strong>中文意译：</strong>“那你现在还在用吗？”“没有。”

这里保留的是嘉宾在现场复述的对话，并非朋友参与本次直播。它揭示了一个容易忽略的区分：持续产出是运行状态，持续被使用才可能说明产出有人关心。是否值得运行，还要考虑收益、成本和后续维护。

### 实验值得继续，但不能跳过领域与价值

Mario 并未排除某些问题领域未来出现有效的 dark factory。他认为需要实验，也需要经济价值。Matt 推测纯数学问题可能比一般应用更容易处理，但这只是临场判断，访谈没有展示领域间的实证比较。

整理者可以谨慎连接前文：目标明确、验证容易的领域，更便于判断自动产出是否达到要求；开放的产品需求、不断变化的环境与用户体验，会让成功条件更难封闭。但这是一种解释框架，需要在具体系统上接受检验。

### 本章小结

软件任务自动化与人的岗位价值需要具体讨论。理解用户、承担系统结果、作出取舍，仍是嘉宾认为有价值的工作。对自动软件工厂，应观察持续使用与经济成效，而不能只展示一个会自动运行的循环。

## 总结与延伸

### 嘉宾的实质收尾：持续决策的疲劳与流程缺口

43:09–45:45，Matt 描述了工作节奏的改变：过去在思考、写代码、再思考之间切换；如今工具承担更多编码，人仿佛持续处于战略判断状态，因此可能更疲惫。

Armin 说自己睡眠不足，也感到这个时期令人兴奋、困惑又陌生。想追上每一项变化的紧迫感会增加压力。Matt 同时提醒，他也在创业，不能将疲劳全部归因于 AI。

Mario 说自己已度过最初过度兴奋的阶段，现在更平静。他在访谈当时尚未看到一套成熟到值得所有组织照搬的工程模式；相较追逐模型变化，他更重视围绕新工具建立工程流程与教学的工作。他肯定了 Matt 和 HumanLayer 等人在这些方向的探索。

> <strong>把注意力预算纳入工程流程</strong>
>
> 整理者延伸：编码加速并不保证决策负担下降。如果每个并行任务都要求人不断审核架构与证据，人的注意力仍可能成为瓶颈。应根据可用理解和审查能力安排工作，而不是仅根据工具能启动多少任务安排工作。

### 将整场讨论压缩成一条责任链

这场访谈可以沿着五个问题贯通。第一，软件为谁服务，什么结果值得获得？第二，哪些接口和功能是必须保留的责任？第三，当前事实与规模允许哪些设计取舍？第四，哪些测试、审查或实际使用证据支持接受实现？第五，系统交付以后，谁仍能够理解它并承担后果？

> <strong>整理者综合：把自动化能力放进完整责任中</strong>
>
> 参考测试集解释了局部自动执行为何进步；公共 API 解释了设计承诺为何仍需谨慎；启动归零案例说明指标必须保留语义；分诊系统说明具体证据能够建立信任；过期规模文档说明证据还依赖当前事实。它们共同指向一件事：让更快的实现服务于清晰且持续成立的责任。

### 可以带回项目的实践问题

以下问题是整理者综合，不是嘉宾发布的标准流程：

1.  开始委托前，说明目标行为、使用者和不能丢失的功能。性能或成本指标也要放在这些要求之中。

2.  遇到开放设计问题，用智能体探索备选实现，再比较其简单性、能力与维护代价。不要把第一个能跑的方案当作唯一选择。

3.  接受修复时，检查复现、修复和回归证据分别说明了什么；关键接口与核心循环需要相应深度的理解。

4.  引用文档中的规模和运行假设时，确认它们仍符合当前现实。

5.  对审查意见和防护代码，追问实际触发条件与结果。达到责任要求后完成工作，避免无价值地延长审查循环。

6.  评价自动化产线时，核查有没有人持续使用，是否提高服务质量，实际价值能否覆盖成本，以及故障时谁能够接手。

### 开放问题与后续学习

访谈留下了多个未解决问题：怎样让形式化规格真正约束持续变化的实现？怎样在减少读代码的同时保留关键理解？哪些领域能形成具有经济价值的自动软件工厂？新工程师又怎样在工具迅速代劳时积累判断经验？

这些问题值得用具体项目回答。可以选一个边界清晰的 bug，记录自动化带来的收益，再选一个开放的 API 设计问题，比较备选方案的取舍。前者帮助校准委托信任，后者帮助训练设计判断。两者结合，比用单一的代码生成速度评价整个工程过程更有解释力。

### 本章小结

模型让执行与探索更便宜，工程判断随之更集中。好的协作需要明确目标、可信证据、当前事实与持续理解。嘉宾在收尾时强调的工程流程建设，正是把这些能力组织成可长期使用的方法，而非持续追逐更多输出。
